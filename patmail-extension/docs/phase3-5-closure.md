# Phase 3.5 收口

Phase 3.5 留下的缺口由 Phase 3.6 的源码修改关闭。本文件只记录这些缺口和对应修复，不把 3.5 报告里的测试次数当作本轮结果。

## 仍开放的问题

- 同一查询条件的分页共用一个由查询键算出的 `querySessionId`。重新查询第一页时，页面快照改成了新文件，有效文件索引仍保留已经消失的旧文件，并继续给出 `SEARCH_RESPONSE_OBSERVED`。
- 重建文件时先展开页面对象。页面额外提交的 `fileDescriptionId`、`customerId`、`caseId` 会留在可信计划里。
- 查询结果没有 `caseId` 时，会退回页面提交的 `caseId`。
- `resolveSelectedFiles` 会在当前账号的多个查询会话里自动寻找同 ID 文件。
- IndexedDB 不可用或事务失败时，`idbPut` 仍正常结束。内存先写入，重启后无法区分是否真的持久化。
- 查询响应返回后才读取当前连接。账号已经切换时，仍可能把结果记到当时的连接上。

## 3.6 如何关闭

- `queryFingerprint` 只表示规范化查询条件。`querySessionId` 由 Background 为每一次查询运行签发。翻页必须带上这次签发的 ID。
- 替换某一页后，按当前仍被有效页面引用的文件重建索引。不再被任何有效页面引用的文件失去来源。
- 可信文件按白名单重建。未经验证的内部 GUID 不进入计划。搜索响应没有的 `caseId` 保持未知。
- 选择必须带上同一次查询运行的 `querySessionId`。来源不一致时标记 `MIXED_QUERY_SESSION`，任务不能视为完整可信。
- 持久化结果分为 `PERSISTED`、`MEMORY_ONLY`、`FAILED`。只有事务完成才记入可恢复存储。
- 请求发出前冻结账号。返回后和记录前再次核对。账号已变化时丢弃结果，不写入新账号的查询会话。

生产邮件写操作和生产流程写操作保持关闭。
