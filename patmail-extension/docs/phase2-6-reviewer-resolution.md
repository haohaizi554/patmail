# Phase 2.6 审核人解析

日期：2026-09-26。

## 候选人从哪里来

顺序固定：

1. `GetFlowSubmit` 节点上的人员候选。响应对应的正文没有保存，所以结构化数组只在 Mock 夹具里使用，并标记为未核对。
2. 已经随流程响应返回的 `cur_user_id` 和 `cn_name` 用来显示当前办理人，不用来代替下一节点候选人。
3. 本阶段不点击页面控件去探测下拉框。DOM 只作为以后的只读补充，当前解析不依赖它。

单个 `user_list_id` 加上一个不含分隔符的 `user_list_name`，可以当成一名候选人。带分号或逗号、或者只有姓名没有 GUID 的字符串，格式记为 `unknown`。

## 本人匹配

当前用户只使用会话里已经确认的 EASY 用户 GUID。匹配条件是候选人 GUID 与这个 GUID 相同。

以下情况都是 `BLOCKED`，不会改选别人：

- 当前用户 GUID 未知
- 候选人没有内部 GUID
- 多个同名候选人，又没有用 GUID 指定
- 当前用户不在候选列表里，即使中文姓名相同
- 调用方指定了另一个人的 GUID

下一节点有多个时，面板列出节点 ID，由用户选择。解析器不会取数组第一项，也不会用中文节点名去猜 GUID。

## 审核动作

`previewReview` 只给出两类结果：

- 当前用户 GUID 等于已选审核人：`PENDING`。表示身份已经对上，审核写接口还没有核对。
- 其他情况：`BLOCKED`。

没有为审核通过生成请求参数。`EndEmailFlowd` 不代表审核通过，也不代表邮件发送成功。
