# 重试

重试按一次 HTTP 请求，不按多步流程。只重试当前这一步，好保住顺序。非幂等的操作避免做成两份。渠道发送和模型请求用不同的信封。

## 对照

| | OpenClaw | Hermes | Claude Code |
|---|---|---|---|
| 渠道 | 默认 3 次，抖动 10%。Telegram 最短 400 毫秒。Discord 发送 500 毫秒，REST 帽 5 分钟 | 适配器自己的发送和编辑 | 无渠道发送重试 |
| 模型 | 限流和瞬时故障走失败转移那份预算。空正文的 400 和 422 不因此变成可重试 | 冷却和回退在失败转移里 | 流中断有自己的恢复 |
| 等待提示 | 单独的 `Retry-After` 不证明用量窗口耗尽。地板长过保存的帽，且配了回退，就直接走回退 | 提供商提示抬高等待 | 无这道帽 |
| Git | `fetch` 和 `ls-remote` 的瞬时失败再试一次。`push` 和 `pull` 不重放 | 更新有自己的阶段 | 无托管 Git 重试 |

## OpenClaw

渠道发送默认 3 次，抖动 10%。共享渠道信封最短延迟 400 毫秒，帽 30 秒，Telegram 和没有覆盖的渠道用它。Discord 发送和 Discord REST 最短 500 毫秒。Discord 发送帽 30 秒。Discord REST 帽 300 秒。这些是按请求的信封。Discord Gateway 的 WebSocket 重连是另一条：最多 50 次，从 2000 毫秒指数退到 30000 毫秒，没有抖动。

空的错误正文不让确定性的 HTTP 客户端错误变成可重试。没有正文的 400 和 422 直接露出，不做静默的错误重提交。带有已识别瞬时证据的客户端错误仍走已有恢复。空的成功响应保留它们单独的响应修复重试。

嵌入运行时里，工具活动之后的模型空闲超时，在最新一批每个工具都有记录的结果、并且全部执行已落定时，也走这份恢复。下一次尝试仍有工具，用来做完任务，包括处理已记录的工具失败。挂起的批准、异步工具活动、有意的工具终止、取消和运行截止，仍阻止这次延续。已完成的动作不重新提交。

Responses 流在终态事件之前结束，也合格做瞬时恢复，包括工具调用还没写完的时候。半截的工具参数从不执行。完成的响应如果工具调用身份不一致，不算断开的流。Gemini 或 Vertex 的流在事件帧内部结束，同样合格。整帧坏掉的 JSON 不合格。

Responses 请求在生成工具调用时碰到输出 token 上限，嵌入运行者在已准入的工具落定之后，也从记录的结果自动延续。模型和账号不变，已完成的动作保留，半截参数从不执行。这次延续共享重试次数预算和运行截止，不共享 90 秒的故障窗口，因为生成一份完整响应可以比那个窗口更长。取消、挂起的批准、活动的异步工作和有意的工具终止仍会停住延续。提供商拒绝和未知的未完成原因不合格。

用尽的订阅、日、周或月用量窗口直接走合格的认证 profile 或模型回退。单独的 `Retry-After` 不建立用量窗口耗尽。临时限流仍遵守提供商的最短等待，上限是保存的 `retry.provider.maxRetryDelayMs`，默认 60 秒。限流地板长过这顶帽时，若配置了回退就直接走回退，因为操作者已经说过服务器要求的等待可以占住运行多久。没配回退时，地板按全长遵守。把这顶帽设成 0 就关掉帽。

原生运行时可以在把终态失败交回 OpenClaw 之前，在内部重试单次请求。那些内部重试和 OpenClaw 的延续预算分开。ChatGPT 的 SSE 错误把 HTTP 状态和 `Retry-After` 一起保留，所以瞬时 HTTP 响应即使消息或提供商代码陌生，仍然可重试。ChatGPT 传输在流式之前，对 `websocket_connection_limit_reached` 单独重连一次。那不是 SSE 的 HTTP 响应重试。

保留内部重试的 SDK 调用里，基于 Stainless 的 SDK，例如 Anthropic 和 OpenAI，可以在可重试响应上收到等待提示，状态是 408、409、429 和 5xx。等待长过 60 秒时，OpenClaw 注入 `x-should-retry: false`，让 SDK 尽快把控制交回。用 `OPENCLAW_SDK_RETRY_MAX_WAIT_SECONDS` 覆盖这道只给 SDK 的帽。设成 0、false、off、none 或 disabled，就让那些 SDK 调用在内部遵守很长的 `Retry-After` 睡眠。

共享的 Git 运行者对瞬时的 `fetch` 和 `ls-remote` 失败再试一次，在命令原来的超时里等一秒。包括不完整的对象传输、连接重置、临时 DNS 失败和瞬时 HTTP 错误。托管的项目克隆用同一政策，并在重试前删掉失败的半成品检出。取消停掉重试。工作区或发布权威在另一次尝试前再查。每次排程的重试写一条 `git/network` 警告，带操作、尝试次数、延迟和退出码。它省略命令参数、仓库 URL 和原始 Git 输出。认证失败、缺少仓库或引用、本地存储失败、进程终止和用尽的命令超时不重试。`push` 和 `pull` 不被这个运行者重放。失败的连接可以跟在一次已接受的写入之后，所以发布保持已有的远程结果对账。这套政策不包住 agent 或安装脚本随意跑的 Git 命令。

Discord 在 429、请求超时、HTTP 5xx，以及 DNS 失败、连接重置、套接字关闭和 fetch 失败这类瞬时传输失败上重试。有 Discord 的 `retry_after` 就用它，否则指数退避。

## Hermes

模型失败的分类、冷却和跨提供商回退写在失败转移里。渠道发送有自己的编辑和对账，没有「3 次、10% 抖动、Discord REST 帽 5 分钟、空正文 400 不重试」这一页共享信封。更新管道的 Git 失败走快照和应用，不把 `push` 排除在一次一秒钟的重试之外当成这套 Git 运行者。

## Claude Code

请求失败可以再试这一轮的收缩或换模型。没有渠道发送的三次信封，也没有「等待提示长过 60 秒就让 SDK 立刻交回控制」的头。
