# 现成调用

对照 `patmail-extension/src`。日期：2026-10-06。

`/读表格` 这类斜杠只把说明贴进这一轮。`workflow/skills.ts` 里的九个本领是字段模板：栏位名、默认值和给用户看的一句话。没有一个本领挂着可执行函数。

能直接跑的是旁边已经写好的函数。模型交选择，函数填内容、做分组或做计划。模型不写脚本，也不替换模板里的 `{占位符}`。

## 占位符

标题和正文共用 `mail/rules/subject-builder.ts` 的 `renderTemplate`。模板是用户事先保存的句子，例如 `{贵方案号}-{发文类型}`。记号写在 `TEMPLATE_TOKENS` 里：文件名称、客户名称、我方文号、我方文号范围、贵方案号、贵方案号范围、客户文号、客户文号范围、申请号、申请号范围、案件名称、文件描述、发文类型、文件数量、日期、公告日。

值来自已经查到的文件。`templateValues` 读 `SelectedPatentFile` 和客户名。`fillFromRules`、`buildBody` 都走这一条。已知记号没有内容时，连同紧跟的一个 `-` 删掉。不认识的记号原样留下，并记进 `unresolved`。

所以占位符不是模型参数。模型若要完成这一步，只指出用哪位客户、哪一批已经查到的文件、哪一套已保存的规则。函数自己替换。缺了哪一格，函数把名字交回来，模型照实说，不编文号。

## 已经接在助手上的

这些由模型提供 JSON 参数，扩展里的函数执行，结果写回工具消息。

`connection_status`、`search_cases`、`search_deadlines`、`list_customers`、`describe_workflows`、`list_skills`、`lookup_api`、`recall`、`remember`、`create_workflow`、`set_workflow_field`、`create_task`。

`create_workflow` 和 `set_workflow_field` 改的是本领栏位，不跑发文。`lookup_api` 只对照文档，不发原站请求。

## 写好了、还没接上助手的

纯函数，输入输出都在扩展里，不写 EASY。

- `renderTemplate`、`templateValues`、`buildBody`、`fillFromRules`：用查到的文件填标题和正文。
- `resolveMailType`：文件描述对上唯一的发文类型。多条映射算冲突，不取第一条。
- `groupWorkflowRows`：按发文方式把行分成一封封。
- `sheetRecipientNames`：从表格行取出收件称呼。
- `resolveRecipients`：在这位客户已启用的模板里取默认或指定的一套。
- `buildTask`：把文件和规则收成一条任务对象。
- `planWorkflow`：在节点唯一、审核人是本人时做出提交计划。计划不是提交。

`automation/state.ts` 里的阶段是目录。`buildStagePlans` 对写阶段一律 `canExecute: false`。`MAIL_CREATE`、`MAIL_SAVE`、`FILE_BIND`、`WORKFLOW_SUBMIT`、`REVIEW_EXECUTE` 不能当成技能去跑。
