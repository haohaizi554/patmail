# 微压缩

大压缩在窗口快满时一次摘要中间一大段。微压缩在每个正常结束的回合之后，只把最老的一轮还没吸收的交换折进一份滚动摘要。默认关闭。打开之后每一轮都会改写已经发送过的历史，前缀缓存每回合作废一次。

## 对照

| | OpenClaw | Hermes | Claude Code |
|---|---|---|---|
| 默认 | 会话卫生和压缩在阈值上成批做 | `compression.micro_compact` 默认关 | 请求前分层裁剪，再考虑自动压缩 |
| 一次做多少 | 选边界后生成结构化摘要 | 每回合只吸收一个交换 | 先预算工具结果，再剪、再折叠 |
| 用户原话 | 压缩摘要替换旧工具结果和旧轮 | 用户消息保持原文，从不被摘要 | 旧用户消息可留在保护尾里 |
| 缓存 | 压缩是允许的缓存断开 | 每回合断开一次，这是打开前要算的成本 | 压缩同样断开缓存 |

## Hermes

长对话最终超出窗口。成批压缩在越过阈值时停下来，一次把中间一大块摘要掉。账单在那一刻集中支付：一次可见的停顿，一次大的摘要请求。

微压缩把同一笔账拆开付。回合已经把回答流式送出，但回合要等这次吸收结束才关闭。每次是对压缩模型的真实调用。它改写已发送的历史，所以提供商的前缀缓存每回合失效。对有些会话，这笔缓存损失大于少停顿的好处。

一个交换是一整轮 agent：一条助手消息，加上它的工具结果和后续助手迭代，直到下一条用户消息。工具重的回合里，token 主要在这里。摘要标记是助手角色。完整交换两侧都是用户消息，角色交替保持合法。

交换从助手消息开始。用户打的字整段会话保持原文。助手产出的多是它做了什么的叙述，摘要损失小。用户指令是意图，不能从后来的工作里重建。把「用现有的重试助手，不要新写一个」缩成一句，几轮之后就会做被禁止的事。

另外两段保持原文。头部是系统提示和开场消息。尾部是按 token 预算留下的最近消息。微压缩只动中间。

压缩器保持一个光标，指向第一条还没吸收的消息。成功一次，光标越过刚摘要的那个交换。选哪一个模型来做这件事，比开关本身更重要。辅助压缩模型可以单独指定。

用户经常粘贴一两万 token 的提示时，这些原文会一直留在上下文里。这是地板，不是漏洞。一条用户提示通常仍远小于一次工具结果。

它不替代阈值上的成批压缩。窗口仍可能因为尾部和用户原文增长而需要一次大的压缩。微压缩让中间不要锯齿式地堆到阈值才突然塌掉。

## OpenClaw

压缩在阈值上选择边界并写摘要。超时可以在没有摘要的情况下提交。已经写进 transcript 的压缩，取消运行不算回滚。没有「每回合吸收一个交换、用户原文永远不动」这道开关。工具结果的 `details` 在送进压缩前剥掉，模型必须读的文字在 `content` 里。

## Claude Code

请求前的分层是：边界、工具结果预算、剪、微折叠、塌缩、自动压缩缓冲。三次失败有断路器。反应式压缩最多一次。这棵还原树里剪、塌缩和反应式有的是桩。

工具结果大约每条 50000 字符、每轮 200000 字符。这是裁剪，不是每回合对最老交换做一次辅助摘要。用户消息是否被摘要取决于自动压缩选中的边界，没有 Hermes 微压缩那种「用户原文永不吸收」的合同。
