# 插件

插件把能力加在核心外面。三家都禁止插件去改循环的源文件。能登记的是工具、钩子、渠道、提供商和命令。发现、启用和真正执行分成几次，这样配置检查不必先把插件代码跑起来。

## 对照

| | OpenClaw | Hermes | Claude Code |
|---|---|---|---|
| 发现 | 清单、工作区、全局根、内置 | `~/.hermes/plugins`、项目 `.hermes/plugins`、pip 入口 | 客户端插件和 MCP 服务器 |
| 独占槽 | 记忆等槽位只能选一个 | 记忆提供者和上下文引擎各一个 | MCP 名单在两轮之间换 |
| 覆盖 | 按来源优先级 | 一般插件后加载的赢；记忆是内置优先 | 用户插件相对内置的合并在客户端 |
| 隔离 | 进程内登记。失败的登记回滚 | 可选的每 profile 宿主进程 | 钩子可以是外部进程或 HTTP |
| 不碰核心 | 走 `openclaw/plugin-sdk`，不 import `src/**` | 不改 `run_agent.py`、`gateway/run.py` | 工具和命令是客户端自己的目录，插件挂在登记面上 |

## OpenClaw

原生插件登记的是能力，不是随便一个回调。文本推理、CLI 后端、嵌入、语音、实时转写、实时语音、媒体理解、转录来源、图像、音乐、视频、网页抓取、网页搜索、渠道、Gateway 发现、迁移，各有自己的 `register*` 方法。只登记钩子的是 hook-only。有工具、命令、后台服务或路由、但没有上述能力的，是 non-capability。两种都还支持。

形状按实际登记分类，不按清单上的自我描述。恰好一种能力是 plain-capability。多种能力是 hybrid-capability，例如一个提供商同时有推理、语音和图像。`openclaw plugins inspect` 打出形状。hook-only 在 doctor 里是信息，不是错误。用了旧的记忆嵌入 API 会警告。配置无效或加载失败才是硬错误。失败登记留在诊断里，贡献回滚，不进入执行范围，也不挡住健康插件和上下文引擎的准入。

四层：清单和发现，启用和校验，运行时加载，表面消费。发现读 `openclaw.plugin.json` 和受支持的包清单。启用阶段决定开、关、阻止，或选进记忆这种独占槽。原生插件在进程内加载，把能力放进中心登记表。托管实例用 Node 跑 JavaScript，需要时编译 TypeScript。兼容包可以先归一成登记记录，而不执行运行时代码。

命令行分成两相。解析前只用 `registerCli` 的描述符占住根命令名。真正的插件模块可以懒到第一次调用再加载。清单和 schema 的校验不执行插件代码。能力快照可以加载受信任的入口来建一份不激活的登记。真正的行为来自 `register(api)` 且 `registrationMode` 为 `full`。

`PluginCache` 在第一次访问元数据时开始填，包括 Gateway 启动前的 CLI 预检。Gateway 启动留下这份主人，并做成不可变的 `PluginMetadataSnapshot`。快照包含所有已配置工作区里的插件元数据，含禁用的，并保留来源优先级。包内容和懒加载的导出不在快照里，而在同一缓存的其它视图。

渠道插件、提供商插件和工具插件走各自的 SDK 页。外部插件在过渡期最稳的仍是钩子。新内置插件优先能力登记。导出的辅助路径不都是稳定合同。

记忆插件若自己拥有存储，压缩前的刷写会把这一轮的记忆受众和沙箱状态交给它。默认的 Memory Core 仍是文件加 SQLite，见记忆笔记。选了别的引擎不自动拆开每个全局插件库。多 agent 时，插件存储要按插件自己的配置切开，不会因为多了一个 agent 就自动隔离。

## Hermes

一般插件从三处来：用户家目录 `plugins/`、项目 `.hermes/plugins/`、pip 入口。后加载的覆盖先加载的。`register(ctx)` 登记钩子、工具、CLI 子命令和语言包。清单里写了 `provides_locales` 的，会登记 `locales/` 下的 yaml。只有清单的语言包不需要 `__init__.py`。

记忆提供者是另一条发现链，内置优先，避免掉进来的目录盖住随包的实现。由 `memory.provider` 按名字激活。没有选中的提供者不会把自己的 CLI 挂进 `hermes --help`。模型提供商懒加载，同名时后写的赢，所以用户家目录里的提供商可以覆盖内置。`PluginManager` 记下 model-provider 清单，但不在发现插件时再 import 一次，否则会构造两份。

上下文引擎和图像生成是各自的 ABC。插件引擎不会自动启用，配置里写上 `context.engine` 才换掉内置压缩器。

插件不改核心文件。缺能力时加的是通用钩子或 `ctx` 方法，然后插件去用。没有具体消费者的钩子不要加。设置走 `hermes memory setup` 和提供者的 `post_setup`，不另开一套顶层命令。

`in_process` 是默认，用户插件进 Hermes 进程。`host` 把每个 profile 的非内置插件放进单独的宿主进程。Hermes 这边拿到的是代理：工具、钩子、命令，以及 ABC 的子类。过不了线的方法集中在一张表里，运行时拒绝和静态审计读的是同一张。宿主进程里不再起宿主。操作者在托管配置里钉了隔离时，插件不能自己选回进程内。子进程环境只带这个 profile 的秘密。

用户代码的每条加载路径要么进宿主，要么拒绝。新的加载器要遵守这一点。目录安装、启用和更新会 `discover_plugins(force=True)`。`on_plugin_loaded` 在这次扫描里发出，说明哪些处理器现在就活着、哪些要等下一会话、哪些 MCP 要等 `mcp.reload`。不要从 RPC 再发一次这个事件。

生命周期钩子由调用方绑好 profile。后台线程用 `spawn_context_thread`。平台插件不把 YAML 写进 `os.environ`，配置进 `PlatformConfig.extra`，门禁用 `platform_gate_env`。

内置路径不再为外部插件保留旧 import。插件靠 `ctx` 和文档里的 ABC。移动内部符号不加重新导出垫片。

离开核心的产品进目录清单，安装记录写在 `.install-metadata.json`，不写进插件树里给 Python 信任。`removed.yaml` 上的仓库，安装、更新、启用和加载都会拒绝。

## Claude Code

MCP 是这棵树里最清楚的外部工具面。服务器在两轮之间刷新工具名单。一轮进行中不改 schema，避免已经发出的 `tool_use` 和下一轮的名字对不上。列工具失败时返回空名单，不把主循环打停。认证是单独的 `McpAuthTool`。资源用列出和读取两个工具，不把资源内容提前灌进系统提示。

插件推荐、市场通知和技能变更是界面钩子，在 `src/hooks` 里。它们可以建议安装，不在回合中途改掉模型正在用的工具表。技能 frontmatter 可以挂自己的钩子，和 MCP 名单一样，用快照挡住一轮中的目录抖动。

协调器、任务板和团队是客户端内的协作，不是第三方插件 ABI。新能力若只服务一个界面，就留在那个界面，不先做一套通用插件协议。这和 Hermes「一个消费者不要先造框架」是同一条判断。

还原树里部分原生模块不在 TypeScript 里。插件能否在这棵树上加载，以调用点和清单为准，不以「目录还在」为准。
