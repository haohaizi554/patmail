# 语言服务

写文件和打补丁之后，先做进程内的语法检查，语法干净再问语言服务器。只把这次编辑新引入的诊断交回去。语言服务器缺失或抖动时，静默退回只有语法的结果，写文件本身不失败。不在 git 仓库里就不启动。

## 对照

| | OpenClaw | Hermes | Claude Code |
|---|---|---|---|
| 何时 | 无这条写后语义诊断合同 | `write_file` 和 `patch` 成功之后 | 编辑器里的语言服务属于 IDE，不一定进 agent 的工具结果 |
| 范围 | 工作区和沙箱的文件工具另有边界 | 工作目录或被编辑的文件在 git 仓库里才跑 | 打开的工作区 |
| 失败 | 工具错误是工具结果 | 语言服务失败不弄坏写入 | IDE 诊断不一定回到模型 |
| 基线 | 无 | 先记下文件上已有的诊断，写入后再查，只表面新的 | 诊断面板显示全部 |

## Hermes

语言服务器作为后台子进程跑，例如 pyright、gopls、rust-analyzer、TypeScript、clangd 等。它们的语义诊断喂进 `write_file` 和 `patch` 的写后检查。模型看到的是这次编辑引进的错误：类型、未定义的名字、缺少的导入、项目范围的语义问题，不只是括号对不对。

不需要编辑器宿主，也不另管一个守护进程。

门闩是 git 工作区。agent 的工作目录或正在编辑的文件在仓库里，才对那个工作区跑。两边都不在仓库里，语言服务休眠。消息网关的当前目录常常是家目录，那里没有项目可诊断，休眠是故意的。

分层是：先做进程内语法检查，微秒级。语法干净才做语言服务。语言服务的每条失败路径都静默退回只有语法的结果。抖动的服务器不能把一次成功的写入变成失败。

每次成功的写入或补丁：先捕获该文件当前诊断的基线，再写，再问语言服务器，滤掉基线里已有的，只留下新的。这样模型不会把仓库里早就存在的错误当成自己刚造成的。

诊断是工具结果的一部分，进入之后的上下文，也受压缩和工具结果预算。它不改文件已经写上的字节。模型要修，就再写一次。

## OpenClaw

文件工具受会话根、沙箱和权限模式约束。写失败是工具结果。没有「写成功之后用语言服务器只报告新诊断，服务器挂了也不失败」这道分层。代码模式和执行批准管的是命令能不能跑，不是类型检查。

## Claude Code

IDE 里的语言服务属于编辑器。agent 的工具结果里不一定有同一份「仅新诊断」的列表，除非某次工具把诊断读回来。写文件的成败仍由工具调用和权限决定。计划模式可以在接受计划前禁止写，这和写后诊断是前后两件事。
