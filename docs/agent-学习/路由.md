# 路由

进来的消息先被渠道接受，再决定哪个 agent 来答，最后决定落在哪把会话钥匙上。回复回到消息来的那条渠道。模型不选渠道。绑定不是门禁。

## 对照

| | OpenClaw | Hermes | Claude Code |
|---|---|---|---|
| 谁答 | 绑定按账号、对端、公会、角色选 `agentId` | 一个 profile 一个家目录。网关按会话键找车道 | 没有渠道。当前项目会话 |
| 私聊 | 默认并进该 agent 的主会话。可改成按人、按渠道 | 私聊是一条会话。群默认按人切开 | 本地对话 |
| 群 | 默认按群隔离。绑定可以把选中的房间并进主会话 | 共享线程才合成一条。发送者前缀加在用户消息上 | 无 |
| 多 agent 同时 | `broadcast` 给每个参与者自己的会话 | 委派和看板是另一条路，不靠入站广播 | Agent 工具开侧链 |

## OpenClaw

渠道是插件，例如 Discord、Telegram、Slack。`webchat` 是内部控制界面，不是可配置的出站渠道。账号 id 是渠道上的一个实例。多个账号时要显式默认账号，否则出站可能落到排序后的第一个。

回复路由是确定的：回到来源渠道。出站目标可以带 `telegram:` 这类前缀，但只在渠道还没选定或选的是 `last` 时当作渠道提示，并且插件要声明这个前缀。已经选了明确渠道时，前缀必须和它一致。`channel:`、`user:`、`thread:` 留在所选渠道的语法里，不另选提供商。插件回执若是失败、抑制或干跑，不改已存路线。确认过的部分发送可以建立路线，请求的内容不会被记成已经全部送达。

私聊默认收成 `agent:<agentId>:main`。`session.dmScope` 可以改成按对端、按渠道对端、或按账号加渠道加对端。绑定可以给自己匹配到的对端覆盖这个范围。即便历史进了主会话，外部私聊的沙箱和工具策略仍用派生的按账号运行时钥匙，不把渠道消息当成本地主会话运行。

群默认 `per-group`：`agent:<id>:<channel>:group:<id>` 或 `channel:<id>`。设成 `main` 会把非私聊对端都送进主会话，提及和回复仍用来源群。Slack 和 Discord 线程在钥匙后加 `:thread:`。Telegram 论坛话题把 `:topic:` 嵌进群钥匙。

主会话被多个私聊共享时，若 `allowFrom` 恰好只有一个具体发送者，非主人的私聊仍记录入站元数据，但不改主会话的 `lastRoute`，避免最后一条路被别人的私聊盖掉。渠道可以标记 `createIfMissing: false`：只更新已有会话的元数据和路线，不因为看见一条消息就建一条只有路线的会话。

选 agent 的顺序是：精确对端、父对端（线程继承）、对端通配、Discord 公会加角色、公会、Slack 团队、账号、渠道通配（`accountId: "*"`）、调用方提供的主人或唯一配置的 agent。多个 agent 又没有主人时，路由报告需要选择，不拿花名册的第一项凑数。一条绑定上写了的字段必须全部命中。同一层里配置顺序的第一条赢，窄规则要写在宽规则前面。省略 `accountId` 只匹配该渠道的默认账号。要渠道级兜底必须写 `"*"`。

绑定只在渠道已经用配对、允许名单和账号规则接受消息之后才被咨询。它不创建账号，也不授权。指向一个渠道从不接受的账号等于没写。未知的 `agentId` 不落到别的 agent。

`broadcast` 让一条已接受的入站消息跑多个 agent。合格的 `渠道:对端` 键优先于不带渠道的旧 WhatsApp 键。每个参与者有自己的会话。合格条目默认要点名、一轮、每个 agent 一回合。`maxTurns` 限制的是各轮启动的参与者运行次数，不是平台上的物理消息条数。Discord、Slack、Telegram 上点名任一合格参与者，可以满足房间的提及门。已配置的 ACP 绑定独占，不参与这套扇出。允许名单仍然有效。

## 机器人互聊

Discord 和 Slack 默认可以接受别的机器人写的消息，仍受提及和访问规则约束。`allowBots: false` 关掉由机器人触发的回合。机器人消息仍可以作为上下文留在对话里，即使不触发回合。

成对循环保护是滑动窗口。核心按账号或范围、对话 id、发送方机器人、接收方机器人记账。A 到 B 和 B 到 A 算同一对。默认 60 秒内 20 次，超出后冷却 60 秒。人写的消息、单机器人部署、自己给自己的过滤，不受这道影响。更窄的房间或账号配置盖过渠道，渠道盖过 `channels.defaults`，再盖过内置默认。飞书只用共享基线。

## Hermes

profile 是隔离的家目录，不是 OpenClaw 那种按渠道绑定选出来的第二个大脑。多路复用的网关在一个进程里按身份服务多个家。入站事件先规范成一份路由身份：哪个机器人收到、谁可以准入、在哪运行。传输 profile 和运行 profile 可以不同，共享机器人转到卫星 profile 是常态。

群默认按人分会话。共享会话才把多个人放进同一条车道，发送者加在用户消息上，系统提示不写死用户名。回复走接收这条消息的适配器。恢复出来的、没有活传输的会话，不拿默认机器人去猜。

没有「一条群消息并行叫醒两个 profile」的广播配置。要多个工作者，用委派或看板，由任务指定受让人。

## Claude Code

没有渠道、账号和绑定。会话属于本机项目目录里的转录。远程和 IDE 接的是同一份会话的另一个界面，不是第二个 agent 绑定。子代理是工具开出来的侧链，不由入站路由表选择。
