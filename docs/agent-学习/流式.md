# 流式

模型可以逐段吐出文字。渠道、桌面和编码客户端各自决定这些片段是预览、独立消息，还是最终那一条。三家都把「正在写」和「已经送达」分开。已经发出去的气泡不能靠后文撤回。

## 对照

| | OpenClaw | Hermes | Claude Code |
|---|---|---|---|
| 给渠道的增量 | 默认不是逐 token。块回复或可编辑预览 | 有的适配器把整段流当成这一条消息 | 终端里逐段画，不经过聊天渠道 |
| 切分 | `EmbeddedBlockChunker`，不切开代码围栏 | 前缀必须稳定，否则整段被重贴 | 工具可以在正文还没结束时开始跑 |
| 终稿 | 重复的媒体去掉；新增的文字仍发 | 由消费方把最终正文交给 `finish` | 工具结果必须配齐，否则下一请求失败 |
| 思考中的状态 | 控制界面有粗粒度启动阶段，第一条正文或工具把它换掉 | 网关用消息或打字指示 | Ink 组件订阅增量 |

## OpenClaw

两层互不替代。块流把助手写完的块当成普通渠道消息发出去。预览流在 Telegram、Discord、Slack、Matrix、Mattermost、Teams 上改一条临时预览。渠道消息没有真正的逐 token 增量。

`chat.send` 被确认后，控制界面可以先显示工作区准备、环境、上下文、模型启动。第一条助手增量或工具开始会永久换掉这轮的启动状态。工具在等批准时，批准状态优先。worktree 和云端派出发生在聊天 run 存在之前，不算这轮的启动状态。

块流默认关（`blockStreamingDefault: "off"`）。`text_end` 是块一切出来就发，并在每次文本结束时冲刷。`message_end` 等到助手消息结束再冲刷；缓冲超过 `maxChars` 时仍会切成多块。分块器在达到 `minChars` 前不发，除非被强制。优先在段落、换行、句子、空白处切开，最后才硬切。代码围栏不从中间切开；被迫在 `maxChars` 切开时先关上围栏再打开，让 Markdown 仍然合法。放得进 `maxChars` 的表格整块走，更大的表格按行切。`maxChars` 不会超过该渠道的 `textChunkLimit`。

连续的块可以再合并。空闲 `idleMs` 后冲刷，超过 `maxChars` 也冲刷。Discord、Signal、Slack 默认合并参数是最少 1500 字、空闲 1000 毫秒，除非另行配置。人味停顿只作用在块回复上，不影响最终回复和工具摘要。默认关。`natural` 是 800 到 2500 毫秒的随机间隔。

预览模式是 `off`、`partial`、`block`、`progress`。`partial` 用最新文本替换同一条预览。`block` 按块追加。`progress` 生成时给状态，完成时给答案。这里的 `streaming.mode: "block"` 是可编辑渠道上的预览，不等于打开普通块回复。普通块回复用 `streaming.block.enabled`。Teams 没有草稿预览的块传输，所以这个模式会关掉原生流，回复改走普通块。Mattermost 在 `block` 下轮换完成文本和工具活动，较早的块留成独立帖子。

Discord 未配置时预览默认关。Telegram 和 Slack 默认 `progress`。Mattermost 和 Teams 默认 `partial`。Slack 的原生 `startStream` / `appendStream` / `stopStream` 只在 `partial` 且需要回复线程时使用。顶层私聊没有那种线程预览，仍可以用草稿帖和编辑。

媒体必须走 `mediaUrl` 这类字段，不从流文本里解析附件命令。这一轮已经发过的媒体 URL，终稿里再出现就剥掉，不发第二遍。终稿若在已发媒体周围加了新文字，文字照发，媒体只留一份。精确重复的终稿载荷被抑制。`before_agent_finalize` 还没决定时，助手回复先扣住。后来的答案替换更早工具轮里扣住的文本，包括最终是 `NO_REPLY`。已经发出去的不撤回。每次被转向的用户输入仍有自己的已送达答案。被替换答案上的媒体可以不带旧标题单独送达。

块流的渠道覆盖必须写成 `channels.<id>.streaming.*`。扁的旧键由 doctor 迁走，运行时不读。

## Hermes

适配器分成两类。普通适配器可以把草稿和终稿分成多次发送。`draft_stream_is_message` 的适配器（例如 Slack 原生流）让这一条流本身就是最终消息。这类适配器有四条从重复终稿事故里留下来的约束：

帧 N 必须是帧 N+1 的字符串前缀。不能在每个 tick 改写草稿：补代码围栏、加光标、在工具边界重置片段、把标准 Markdown 转成 mrkdwn，都会让渠道把整段快照再贴一次。终稿变换只发生在真正结束时。

谁结束由消费方宣布。`finish(final_text)` 带上完整的最终回复，包括校验脚注。流发出去之后再改 `final_response`，会让「已送达的终稿」和存储对不上，然后纠错再发一条。

不是终稿的发送，例如解说、片段尾巴，要标 `metadata["_interim_send"]`。否则封口逻辑会把这段临时文字当成流的结尾。`send` 和 `send_for_platform` 两道出口都做这个检查。新的出口要同样检查。

终稿若必须出现在已经封口的流旁边（排队的后续、带媒体的终稿），先按消费者的 `message_id` 编辑。没有可编辑消息时才普通发送。封口后的原生流就是一条普通消息，编辑仍然有效。

可重试错误在 OpenClaw 那边有 15 秒宽限。Hermes 这边流的终态以消费方的 `finish` 为准，不由适配器猜测模型已经说完。

桌面和 TUI 走另一条增量：`message.delta` 到 `message.complete`，工具是 `tool.start`、`tool.generating`、`tool.complete`。这是界面事件，不是渠道气泡。

## Claude Code

`StreamingToolExecutor` 在模型还在写的时候就开始执行已经完整的工具调用。只读、标了可并发的调用并行。写文件和有副作用的命令独占。一个 Bash 兄弟失败可以中止其余兄弟，这一轮不因此结束。

模型中途换成另一个模型时，执行器 `discard`。旧的 `tool_use` id 不能进入下一次请求。半截参数不执行。

工具结果大约每条 50000 字符、每轮 200000 字符。超出的落到 `tool-results/`，消息里留指针。缺结果会补一条，否则接口 400。

界面用 Ink 画增量。钩子执行有单独的事件总线：`started`、`progress`、`response`，和主消息流分开。没有订阅者时最多积 100 条，多了丢掉最旧的。`SessionStart` 和 `Setup` 总是发出。这是钩子进度，不是渠道预览。
