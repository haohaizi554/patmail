# 积压

已经就绪的多条后台完成，在交互界面上收成一轮通知。这不加延迟，也不保证把不同时刻结束的任务并成一批。整批都被人读过或杀掉，就不再开一轮。观看输出和委派结果仍是各自的通知，按原来的顺序，不折进完成批次。

## 对照

| | OpenClaw | Hermes | Claude Code |
|---|---|---|---|
| 合并 | 完成叫醒原会话。失败即使别人忙也叫醒 | 同一对话里已经就绪的完成收成一轮 | 任务列表逐条显示 |
| 延迟 | 不靠合并去等下一条 | 不加延迟 | 无 |
| 消费 | 取消不发完成通知 | `process_manage` 的等待、日志或杀死可以抑制 CLI 完成，即使进程已经离开登记处、进了输入队列 | 读过的工具结果留在转录 |
| 系统提示 | 完成是新的一轮或系统事件 | 批次和投递状态不写进系统提示 | 无 |

## Hermes

交互表面把同一条对话里已经可以投递的连续后台完成收成一次通知回合。失败和成功的输出都留在这批里。只有一条时，保持原来的文字。

进程身份一直留到分发。因此显式的 `process_manage` 等待、日志或杀死，可以在完成已经离开进程登记处、进入输入队列之后，仍抑制 CLI 的那次完成。整批都被这样消费掉，就不开回合。

观看输出和异步委派的结果仍是分开的通知，保持原来的顺序，不折进完成批次。

经典 CLI 拥有空闲和回合后的排干，以及压缩感知的所有权和最终输入的拆包。TUI 和桌面在核对所有权之后，把轮询器里已经就绪的快照分组。每个进程仍发出自己的界面状态。忙碌的会话把结构化事件重新排队，而不是把已经渲染好的批次字符串再排队。回合后的安全网走同一条路由和渲染。桌面和仪表盘聊天共用这个后端。

消息网关已经按路线做短窗口的批处理。交互积压不替换那套机制，也不改适配器的发送。非交互的 API 请求、ACP 客户端和一次性 CLI 不会因此多出一条自己的通知环。

共享的渲染是进程通知批次。批次和它的投递状态都不进系统提示。写明了收件人的事件仍要有可证明的主人。另一条活会话不能领养它们。委派的投递仍走已有的耐久领取账本，按一次委派，而不是按一批进程。

## OpenClaw

后台命令在启动它的那条聊天里完成。失败会叫醒起源会话，即使别的会话正忙。起源还在跑就等到空闲。人工取消不发完成通知。子代理不会被后台 exec 自动叫醒，要自己去取。这些是单条完成的规则。没有「已经就绪的多条收成一轮、整批被消费就不开回合」这份交互积压合同。心跳的投递目标不用于这次继续。

## Claude Code

后台任务的输出回到工具结果或任务列表。没有跨多条完成的合并回合，也没有「另一条活会话不能领养写明收件人的事件」这道主人证明。取消停的是这一轮或这一任务。
