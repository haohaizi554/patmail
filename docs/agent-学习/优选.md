# 优选

OpenRouter 可以把同一次请求分给不同的底层提供商，并按价格、速度或质量排序，也可以只允许或排除一些名字。Nous Portal 自己决定路由，调用方带上的 `provider` 对象不会送出去。这份配置在 Portal 上被忽略。

## 对照

| | OpenClaw | Hermes | Claude Code |
|---|---|---|---|
| 谁选底层 | 模型引用是 `provider/model`。认证 profile 在同一提供商内轮换 | `provider_routing` 只对 OpenRouter | 客户端选的就是那个模型 |
| 排序 | 备用链是另一对模型，只活这一轮 | `sort`、`only`、`ignore`、`order` | 无 |
| 门户 | 无这层调用方偏好 | Portal 不接受调用方的提供商偏好 | 无 |
| 和备用 | 用户选中的模型是严格的 | 凭据池先轮换钥匙，再换备用模型。优选是同一把 OpenRouter 请求里的底层 | 无 |

## Hermes

OpenRouter 后面有多家推理提供商。`provider_routing` 写在配置里。`sort` 决定按什么排，例如价格。`only` 是白名单。`ignore` 是黑名单。`order` 是明确的优先顺序。`require_parameters` 为真时，只用支持全部参数的提供商。`data_collection` 可以允许或拒绝数据采集。

这不是换 Hermes 的 `model.provider`。聊天模型仍是 OpenRouter。变的是 OpenRouter 把这一次请求交给谁。前缀缓存跟账号和钥匙。底层提供商若变了，缓存是否还在由 OpenRouter 决定，不由这份排序保证。

Portal 按模型集中路由。Hermes 从不把 `provider` 对象发给 Portal。配了 `provider_routing` 也不生效。要控制 Portal 用哪一家，换模型，而不是写这节。

凭据池和备用链仍在外面。池用尽才换备用提供商。优选发生在「已经决定用 OpenRouter」之后。内容策略失败不因此去试 `ignore` 列表里的下一家。那是错误分类，不是排序。

## OpenClaw

模型引用已经包含提供商。`openai/模型` 不因为前缀就选 Codex。运行时策略未设时，只有精确的官方 HTTPS Responses 路线才可能隐式选 Codex。备用是配置里的下一对模型，只用于这一轮。没有 OpenRouter 式的 `only` 和 `ignore` 写在同一次请求上。认证 profile 的轮换是同一提供商的不同钥匙，为的是缓存和额度，不是底层推理农场的价格排序。

## Claude Code

请求发往客户端配置的那一个端点。没有调用方的提供商排序对象。换模型就是换会话里的选择。
