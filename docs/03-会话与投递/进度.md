# 进度

长时间工作时，渠道上保持一条可编辑的进度消息，而不是堆一串「还在做」。真正的工作开始才创建。最终答案另交付。中间的工具失败和命令的非零退出默认不进这条草稿。

## 对照

| | OpenClaw | Hermes | Claude Code |
|---|---|---|---|
| 形态 | `streaming.mode: progress`。一条消息反复编辑 | 活动条和工具事件。流即消息的渠道要求草稿是前缀 | 客户端里的工具行 |
| 默认 | Telegram 默认进度。Discord 的预览默认关，要显式打开 | 按渠道适配器 | 始终在本地界面 |
| 失败 | 默认不写进草稿。`toolProgress` 才加入滚动工具日志 | 工具完成事件带成败 | 失败的工具结果留在转录 |
| 静默 | 进度不是终稿。`NO_REPLY` 仍可以只留下媒体 | 临时发送要标 interim，避免被封成终稿 | 无渠道草稿 |

## OpenClaw

把 `channels.<channel>.streaming.mode` 设为 `progress`。真正的工作开始后创建一次消息，agent 阅读、计划、调用工具或等待批准时编辑它，然后交付最终答案。默认草稿有状态标题、写好的计划步骤和批准请求。中间的工具失败和非零命令退出留在草稿外面。`streaming.progress.toolProgress` 打开后，加上滚动的工具日志，包括失败，例如一行 Bash 和它在跑的测试。

Discord 的预览流默认关。要进度就显式设这个模式。Telegram 默认就是进度，不必再配。两边都可以改成 `partial`，改为流式回答正文。块回复和进度草稿是不同模式。进度草稿是一条状态，部分模式是回答文本的增长。

这条草稿不是终稿。最终答案仍按渠道限制送出。静默记号不把进度条当成已经回答了必答回合。批准还挂着时，草稿可以显示正在等批准。批准卡片本身仍是批准，不是草稿里的一行字。

和块流、前缀稳定的渠道流不要混成一种。进度模式编辑的是状态行。流即消息的适配器要求每一帧都是下一帧的前缀，那是另一条合同。

## Hermes

工具开始、生成中和完成是界面事件。桌面和 TUI 用它们画活动，不靠去编辑一条 Telegram 消息，除非适配器自己这么做。流即消息的渠道把一条累计流当成最终消息。草稿必须前缀稳定。不是终稿的发送要标成临时，否则临时状态会被封成最终文本。终稿要改已发出的消息时先编辑，没有可编辑的 id 才新发。

后台命令的完成回到原会话，可以是新的一轮，不是去改进度草稿。心跳事件只有增量输出。

## Claude Code

工具活动出现在客户端的转录里。没有「一条渠道消息从计划步骤编辑到最终答案」的 Gateway 模式。流式工具执行把结果尽早配上，界面可以先显示工具已开始。最终助手消息就是终稿。
