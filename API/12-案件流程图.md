# 案件流程状态

要看一条处理事项下面的配案、核稿、递交、发文停在哪，调 `GetCaseBusFlow`。处理事项表 `GetProcList` 只有事项级的 `proc_status`，没有这些子流程的节点。

发文邮件自己的审批流是 [08-流程审批.md](08-流程审批.md) 的 `GetFlowInfo` / `GetFlowHistory`，不是这个接口。

Handler：`POST /AjaxServers/CaseInfo.ashx`。页面 `CaseManage.aspx`，脚本 `Scripts/Page/Patent/CaseAddForPa.js` 的 `LoadFlowList`。悬停单节点是 `ShowFlowInfo`。

`ClientInfo.Result` 可以是 `false`，同时 `Status` 为 `true` 且业务数组有数据。先看数组在不在。

下面节点名、意见文字、`node_code` 除 `END` / `FIRST` 以外的取值，都来自一份响应，不是封闭枚举。换一个案件，名称和代码会变。读状态用结构，不把这份响应里的字写死。

---

## 状态怎么读

1. `Call=GetCaseBusFlow`，传入 `case_id`。
2. 在 `ProcInfo` 里用 `proc_id` 找到要看的处理事项。
3. 在 `Eflow` 里留下 `proc_id` 相同的行。再按业务用 `eflow_name` 挑子流程（发文、配案、核稿、递交，或其他返回值）。同一个 `id` 是同一条流程。一个事项下可以有多条同名子流程，不能取数组里的第一条，也不能看见另一条已经结束就当成这一条结束。
4. 该 `id` 下 `order_by` 为 `2` 的那一行是当前节点。页面把 `2` 当成正在进行，其余当成已经办过。已经办过的行在这份响应里 `order_by` 都是 `1`，读的时候仍按「是不是 `2`」判断，不要假设已办永远是 `1`。
5. 当前节点 `node_code` 转成大写后是 `END`：这条子流程已经结束。
6. 当前节点不是 `END`：还停在这一行的 `node_name` 上。`node_code` 允许是空字符串，空不是结束。
7. 还没走到的节点在 `Activity` 里。用当前节点的 `history_id` 对 `Activity.obj_id`，并且 `node_code` 相同，它后面、同一个 `obj_id` 的行才是未到达。未到达不能当成已审核。模板里有结束节点，只说明流程定义里有这一步。
8. 已办节点的办理动作不在 `Eflow` 上。要用该行自己的 `history_id` 调 `GetFlowNodeInfo`，读 `FlowInfo.audit_type_zh_cn`。这是这一步的办理结果，不是整条流程的状态。流程结束与否只看第 5 步。

不要用来判断子流程状态的字段：

| 字段 | 原因 |
|---|---|
| `GetProcList.proc_status` | 事项级。事项可以是完成，下面某条子流程还没结束；也可以是空，子流程已经在中间节点 |
| `ProcInfo.proc_status` | 流程图接口里的事项状态。可以和表上的 `proc_status` 不一致，也可以是空 |
| `ProcInfo.finish_date` | 事项完成日，不是子流程节点 |
| `Eflow.audit_time_ss` | 当前节点也会带时间。页面在 `order_by` 为 `2` 时不显示它 |
| `Eflow.remark` | 办理意见，自由文本 |
| `Eflow.seq` | 等于事项的 `ProcInfo.seq`，不是节点顺序 |

节点从左到右的顺序，是同一个 `id` 在 `Eflow` 数组里的先后。`Activity.seq` 才是模板上的节点顺序。

## GetCaseBusFlow

只读。

| 参数 | 必填 | 说明 |
|---|---|---|
| Call | 是 | `GetCaseBusFlow` |
| case_id | 是 | 案件 ID |
| log_pagename | 否 | 页面传 `CaseManage.aspx` |

顶层：`ProcInfo`、`Apply`、`Eflow`、`Activity`、`ClientInfo`。

### ProcInfo

事项列表。字段：

```text
proc_id, seq, ctrl_proc, ctrl_proc_code, proc_status,
create_time, create_time_dd, create_time_mm, create_time_ss,
finish_date, finish_date_dd, finish_date_mm, finish_date_ss
```

`ctrl_proc_code` 为 `NEW` 的是开卷。开卷的提案在 `Apply`，不在 `Eflow`。开卷上的子流程还要站点配置 `NEW/SHOWFLOW` 打开才画；其他事项有 `Eflow` 就画。`ctrl_proc_code` 可以是空字符串。

### Eflow

子流程节点。字段：

```text
id, proc_id, case_id, seq, eflow_name,
history_id, node_code, node_name, order_by,
cn_name, user_name, remark,
audit_time, audit_time_dd, audit_time_mm, audit_time_ss,
create_time, create_time_dd, create_time_mm, create_time_ss
```

没有 `audit_type`。

画面文字是 `cn_name(node_name)`。`user_name` 页面画历史节点时不用。日期字段带 `_dd`、`_mm`、`_ss`。`audit_time` 是日期，`audit_time_ss` 到秒。

这份响应里，当前节点（`order_by` 为 `2`）的 `history_id` 等于该组 `id`，已办节点各有自己的 `history_id`。用 `history_id` 去对 `Activity`、去调 `GetFlowNodeInfo`。已办节点传它自己的 `history_id`。

### Activity

每条子流程的节点模板，结束了的流程也会返回。按 `obj_id` 分组，`obj_id` 对得上 `Eflow` 当前节点的 `history_id`。字段：

```text
obj_id, flow_id, list_id, node_id, seq, next,
node_code, node_name, node_name_en_us, node_name_ja_jp,
node_type, user_name, user_list, allow_edit, allow_skip
```

`seq` 是模板顺序。`next` 是下一节点的 `seq`，最后一节点这份响应里是 `"0"`。`node_type` 为 `U` 的是办理节点。`allow_edit` 在结束节点上为 `false`。`allow_skip` 类型不统一，空字符串和布尔都会出现。这里的 `user_name` 是候选人名单，和 `Eflow.user_name` 不是一个字段含义。

### Apply

只对应开卷的提案。字段：

```text
history_id, node_code, node_name, cn_name, order_by, audit_type,
audit_time, audit_time_dd, audit_time_mm, audit_time_ss
```

`order_by`、`node_code` 的读法和 `Eflow` 相同。提案这里直接有 `audit_type`，子流程没有。

## GetFlowNodeInfo

查一个已经出现在 `Apply` 或 `Eflow` 里的节点办了什么。`Activity` 里还没走到的节点没有这条记录。

| 参数 | 必填 | 说明 |
|---|---|---|
| Call | 是 | `GetFlowNodeInfo` |
| history_id | 是 | 该节点的 `history_id` |
| log_pagename | 否 | 页面传 `CaseManage.aspx` |

有记录时顶层是 `FlowInfo` 对象：

```text
node_name, audit_cn_name, audit_type_zh_cn, remark,
audit_time, audit_time_dd, audit_time_mm, audit_time_ss
```

`audit_type_zh_cn` 是这一步的办理结果，原样使用，不映射成固定的「待审 / 通过」。没有 `FlowInfo` 时页面显示「查无信息」，调用方应当成这一步没有办理记录。

---

## GetProcList

事项表，不是流程状态。`Case.js` 的 `CaseManage.GetProcList`。

顶层 `TableRows`、`CaseInfo`、`ClientInfo`。行上有 `proc_id`、`ctrl_proc`、`ctrl_proc_code`、`proc_status`、`finish_date`、`review_stage`，没有 `eflow_name`、`node_code`、`order_by`。和 `GetCaseBusFlow` 用 `proc_id` 对齐即可。状态不要从这里取。

## 一份对照

`183.36.43.66.har` 里一笔案件的响应，只用来对上字段。仓库里的 `HAR/流程信息-PCT` 没有正文。

`GetCaseBusFlow` 的 UTF-8 长度是 23415。`ProcInfo` 4 条，`Apply` 3 条，`Eflow` 16 条，`Activity` 17 条。同一案件里发文有两组 `id`：一组当前节点不是 `END`，另一组当前节点是 `END`。所以同名子流程必须按 `id` 分开读。

`GetFlowNodeInfo` 这次只点到了已办节点，`audit_type_zh_cn` 的返回文字是「提交」。这是样本里的办理结果，不是状态代码表。
